Start here
We are building an open engineering platform in which a user directs Postdoc, an AI research 
coordinator. The work should remain understandable from the original question through sources, 
estimates, calculations, equipment, actual results, and useful shared knowledge.
The recommended first achievement is one investigation that stays understandable when you return 
to it. You can recover the question, inspect the inputs and their origins, repeat a supported calculation, 
and see what remains uncertain. Postdoc should be able to use that record, work within limits, and 
explain what it did.
The first scientific case is now a bounded investigation of cellulosic ethanol: begin with a documented 
corn-stover case and batch conversion, then add alternatives only where suitable evidence and 
models exist. Downstream recovery may use a different operating mode. The platform's wider mission 
remains intact; this case gives us a concrete way to develop and test it.
That first achievement is smaller than the whole vision. It establishes a foundation on which 
experiments, equipment histories, collaboration, and independent reproduction can build. The full 
scope remains visible in the coverage map at the end.
Your role Decide whether the work answers a useful question and whether its behavior and 
explanation make sense. You do not need to choose a database, read code, or write detailed 
programming instructions.
The development team's role Investigate the existing software, make and explain technical 
decisions, build the agreed behavior, check it, repair relevant problems, and show you the result. 
Technical and scientific claims need evidence beyond an attractive demonstration.
The immediate next step Establish a running baseline and select one existing calculation for the first 
corn-stover investigation. Inspect BioSTEAM and its reference models as possible dependencies after 
that baseline. The repository already contains useful tools. We should preserve them and complete 
the missing connections.
The first prepared assignment Save an investigation with a sourced input and a labeled estimate, 
connect it to an existing balance or recovery calculation, reopen it, amend it, and export an 
understandable account. A full new ethanol model is not a prerequisite. Section 6 describes what you 
will review.
This document develops the product brief, roadmap, decisions, and first assignment. Technical Codex 
prompts and software implementation remain for a later stage. No product code, deployment, or 
licence terms have been changed to prepare this plan.

1 The project brief
What we are building
openFerment should help a person turn an engineering question into work they can inspect, test, and 
improve. Its first domain is bioprocess engineering. A broader architecture can support other process 
and manufacturing disciplines as appropriate tools and evidence are added.
The Home experience should be a conversation with Postdoc inside a chosen project. The user can 
inspect the plan, supporting work, spending, unresolved questions, and decisions. Important results 
also exist as records the user can open directly. Conversation should not be the only way to find 
them.
Postdoc coordinates specialist agents and software tools. It should choose work suited to the 
question, keep useful continuity, offer clearly identified estimates, and explain what the evidence 
supports. More agents are useful only when they improve the work.
The first flagship question is which supported batch-conversion choices are promising for a 
characterized lignocellulosic material. Corn stover comes first. Switchgrass is a conditional second 
case, contingent on suitable reference data and a checked model. This is not a promise to optimize 
any feedstock or to establish the best commercial use of any biomass resource.
Postdoc also needs a deliberate place for ideas. It may propose an unconventional explanation or 
process change without identifying a particular source in its training. That proposal remains a 
hypothesis until evidence supports it. Engineering evaluation, experimentation, and a useful idea are 
distinct achievements.
The platform includes the machinery and manufacturing knowledge needed to make a process real. A 
useful public contribution may include editable designs, fabrication methods, controls, commissioning, 
maintenance, observations, economics, and failures. It should help another competent team 
understand and reproduce the work.
What guides the decisions
The purpose is to create useful wealth and share the means to create it. Public contributions should 
be practically usable under real permissions, including for commercial work. Private user projects can 
coexist with the commons.
Origins, uncertainty, responsibility, and rights should remain visible through the work. An estimate can 
be useful without becoming a measurement. A successful prediction can be informative without 
proving every assumption. A signature can identify an approval without proving the underlying claim.
One foundational hypothesis is that reusable scientific tools and records help a capable AI produce 
more dependable work with less repeated effort. We will compare the specialized workflow with a 
competent general agent using the same underlying model and comparable resources. Better quality, 
lower cost, and the value of specialized agents are things to test; none follows automatically from the 
architecture.
The nonprofit is a proposed legal and economic support for the shared project. The founder's possible 
company is an example of participation. Neither should organize the software around special 
privileges for one business.

Two other connections need particular attention
The browser can record reconciled measurements, but the inspected service explicitly describes

Existing model configuration includes a primary model, fallback, roles, and spending information. That

What the new scientific case adds
BioSTEAM offers reusable process and economic modeling foundations. Its comparative example 
includes corn stover with dilute-acid pretreatment and switchgrass with AFEX. Those examples do not 
establish a calibrated model for every crossed feedstock/pretreatment pairing. The tutorial's illustrative 
uncertainty assumptions are not experimental uncertainty evidence. [5]
The historical NREL corn-stover design is a useful reference with mixed operating modes and a 
stated historical economic basis. It is not a ready-made batch-only plant or a current price quotation. 
BioSTEAM already includes batch-sizing tools; inspect and reuse appropriate components before 
proposing a new engine. [6]
None of those dependencies was installed or executed in preparing this update. The baseline should 
record versions, permitted reuse, operating assumptions, and the smallest reproducible reference. 
Reproducing software output, reconciling it with a published design, and checking prediction against 
independent observations are separate tasks.
3 One example we will follow
The recommended starting question
Use a calculation already supported by the software to examine a narrow part of a documented corn-
stover ethanol scenario. A suitable question is: for a fixed, stated conversion scenario, how does 
changing one assumed product recovery affect the estimated amount remaining, and which missing 
information limits that answer?
This is a planning example, not a selected experimental protocol or a claim about real equipment. A 
product balance can be checked without constructing a new pretreatment or biological model. The 
baseline review should choose the smallest existing case that supports a clear answer. If the needed 
conversion model is absent, preserve a documented fixed conversion input and state that boundary. 
You should confirm the question's usefulness; the team chooses and explains the technical details.

The scientific boundary
The flagship requires batch biological conversion. The first case brief names the hydrolysis and 
fermentation stages included in that batch block; it does not silently require every upstream operation 
to be batch. Charging, processing, transferring, emptying, cleaning, vessel use, and downtime must 
be stated where they affect output. Recovery, finishing, and utilities may operate differently; record 
each operation's mode and the assumptions connecting them. Do not call a mixed-mode reference a 
fully batch plant, or require a new batch distillation model merely to use it as a reference.
A feedstock record needs sample or lot identity, composition basis, units, analytical method where 
known, and unresolved fractions. Dry and as-received values are different. Composition alone does 
not determine digestibility, inhibitor response, strain behavior, or successful conversion. Missing 
characteristics stay missing. A range of conditional scenarios is useful when a predictive model is not 
supported. [7]
Start with one documented feedstock, pretreatment, organism, and operating-condition pairing. Add 
another only with appropriate evidence. Vary operating conditions only when an applicable response 
relationship connects them to performance. An assumed yield is not automatically a controllable 
optimization variable.
The output should say best among the supported, feasible alternatives under the recorded 
assumptions. A conversion-only result or a provisional recovery factor is not a complete plant design. 
Plant-wide minimum selling price requires a consistent economic boundary, product specification, 
usable annual output, timing, recovery, utilities, waste handling, capital, and financial assumptions. 
Missing parts cannot silently become free.
The journey through the platform
You name the investigation and explain the decision you want to make. Postdoc finds relevant 
existing work and proposes a bounded analysis. You can inspect the sources and recognize which 
inputs are measured, quoted, calculated, estimated, or assumed.
The analysis runs through a supported calculation. You can follow the result to its exact inputs, 
method, and conditions. You close the application and later recover the work. Changing an input 
produces a linked revision while the old result remains understandable.
Postdoc may propose a variation alongside that work. Its record explains the idea, basis or absence 
of a traceable source, applicable conditions, assumptions, and proposed check. A supported 
calculation can screen it; unsupported parts remain research questions. Evaluation can reject, revise, 
or retain it without deleting its history.
When a real test becomes appropriate, the team records its procedure, actual machine, expected 
outcome, and planned observations before the work. Actual results return to the investigation. 
Postdoc explains what matched, what did not, and which questions the test cannot answer.
Equipment and economic records deepen the same example. A particular machine has its own 
construction and operating history. A permitted release gives another team enough information to 
inspect and repeat the supported work. A later reproduction or increase in capacity supplies its own 
evidence.

What counts before a new experiment exists
Example data can exercise the software when clearly identified. Historical observations can be 
imported with their real origins. Neither should be described as a new experiment performed through 
openFerment.
A useful software release can precede physical proof if it states that boundary honestly. Work that 
does not depend on a new experiment can continue while physical arrangements are prepared. The 
evidence that remains missing must stay visible.
4 The promises we must preserve
The user directs the work
The user chooses goals and limits. Routine searches, calculations, and drafts can proceed within 
delegated authority. Spending, record changes, release, and physical control have permissions 
appropriate to their consequences. The application must enforce those permissions rather than 
relying on a model to remember them.
Information keeps its meaning
Important inputs retain their origin, units, conditions, and limitations. Calculations preserve their input 
choices and versions. Connected tools agree about streams, composition, units, time, and scale. 
Charts and exports carry the context needed to interpret them.
Confidence should reflect relevant evidence and methods. One universal trust score is not a 
substitute for explaining why information applies to a particular decision.
Keep origin, applicability, and review status separate. A published measurement can be well sourced 
yet poorly applicable to a new feedstock. An expert-reviewed estimate is still an estimate. A 
calculation does not convert its assumed inputs into observations.
Distinguish real material or process variability from gaps in knowledge, measurement error, and 
limitations of the model itself. Use unknown, a conditional scenario, a supported interval, or an 
evidence-based probability distribution as appropriate. Preserve important dependencies: composition 
fractions must respect closure, and related yields cannot always vary independently. Do not invent a 
numerical confidence or a physical probability from an LLM's confidence, sampling temperature, or 
frequency of generating an idea.
Ideas have a lifecycle
Give a hypothesis an identity, generating context, model and instruction version where available, and 
an explicit next check. Keep the original proposal and the reasons for later changes. Record whether 
it is proposed, screened within model limits, awaiting evidence, contradicted, or supported under 
stated conditions. Approval to investigate is not scientific validation. Claims of novelty need 
appropriate review.
The scientific library is deliberate
The initial evidence base is a small, curated, versioned set of permitted papers, extracted data, 
equations, reference cases, and installed tools. Updates do not silently rewrite old results. Retrieved 
or imported text is evidence to inspect, not authority to change system permissions.

Postdoc uses an authorized model API. It has no independent web-search capability by default; 
simulation and optimization components do not perform research or fetch arbitrary content. User-
requested acquisition or deliberately imported literature can update the library through a recorded 
process. Record source, access and reuse rights, extraction, review, and library version before relying 
on new material. Controlled acquisition is separate from model inference and does not imply locally 
hosted inference.
Useful work can be recovered
The investigation preserves the question, decisions, supporting work, and unresolved issues. 
Corrections remain attributable. Earlier results do not quietly change when someone edits an input. 
Recovery and export should be demonstrated, not inferred from the presence of a save button.
Real outcomes support limited conclusions
Predictions are recorded before outcomes. The project retains misses and inconclusive results as well 
as successes. A final result does not automatically validate all upstream parameters. A machine or 
process retains the conditions and scale at which its performance was demonstrated.
Public knowledge is deliberate and usable
Private projects remain private within the supported operating arrangement. Public contributions carry 
attribution, useful source files, and actual permissions. Training on project data needs its own 
authority. Openness of the software does not automatically make every user's work public.
We preserve the ability to change course
The team should justify major changes, preserve recoverable versions, and update the record of 
decisions. New tools, providers, agents, and domains must show useful behavior and evidence. 
Detailed architecture, legal terms, and future model-training methods remain choices to investigate.

Purpose Find out whether the knowledge transfers, then investigate larger output as a separate

Still outside this milestone Calling a larger design validated before it is tested, or treating one

Continuing development Expand useful capability
Additional biological tools, recovery operations, economic models, providers, training, team features, 
and engineering domains should follow the same pattern: a useful question, bounded work, relevant 
evidence, and an honest claim.
For the ethanol case, suitable later assignments may add a supported response relationship, limited 
operating-variable search, batch timing, sensitivity, and a second feedstock pairing. Switchgrass 
remains conditional. Arbitrary mixed waste, generalized inhibitor prediction, automated global 
flowsheet synthesis, all pretreatment methods, complete dynamic scheduling, detailed environmental 
claims, and autonomous experiments belong outside the initial commitment. A broad market-use 
question such as what to do with alfalfa must not silently become an ethanol-only optimization.
Teaching and competence support can develop alongside the workflow where users need them. 
Operators and fabricators must have ways to contribute corrections and receive credit. They should 
not wait for a distant final phase to be heard.
Learning begins with a visible track record, corrected inputs, useful retrieval, better route selection, 
and better experiments. Fine tuning or reinforcement learning is a later option if permitted data and 
independent evaluations show a benefit. No fixed number of experiments makes it necessary.
The milestone order reflects dependencies, not an artificial ban on parallel work. Equipment 
preparation, legal stewardship, and suitable learning materials may proceed alongside software where 
useful. No calendar or delivery budget is promised before the baseline and work estimates exist.

Why it matters Postdoc cannot be a dependable research coordinator when its answer outlives the 
records explaining it. One small saved investigation gives later agent work and measurement return 
something coherent to connect to.
The user's situation I have a narrow corn-stover ethanol question, a documented starting quantity, 
and an estimated conversion or recovery input. I want to use an appropriate input in an existing 
supported calculation, understand why it was used, and recover that explanation when I return. A 
simple product balance is enough; it does not establish the biological conversion or the physical 
recovery design.
What I should be able to do
1. Name the investigation and state its question, corn-stover reference conditions, process boundary, 
and intended decision. Identify batch conversion and state any separate recovery assumption.
2. Keep a sourced value and an estimated value from the curated reference set or user input. See 
units, composition or quantity basis, origin, applicability, review status, responsible person or tool 
where applicable, and important limitations. Unknown information remains unknown. A numerical 
range is included only when there is a defensible basis for it.
3. Use a suitable estimated input in one existing supported calculation. Open its result and follow it to 
the exact input and method version used. Its estimated origin and limitations remain visible in the 
result and export. Keep a sourced input in the same investigation so the distinction can be 
inspected.
4. Close and reopen the application and recover the work in its supported operating arrangement.
5. Amend an input and make a new result while still being able to inspect the earlier input and result.
6. Export an understandable account containing the question, selected inputs, origins and limitations, 
calculation reference, and relevant versions.
The demonstration you will review
Use one clearly identified example. Walk through the six actions in order, then let you find the source 
or estimate's basis without being coached through obscure menus.
Show the old and new results together. Explain whether a changed input affects other saved results 
and how the user can recognize that they may need review.
Then show missing required information, incompatible units, and a failed save. The application should 
explain what was not saved and what can be retried or recovered. A result should not appear saved if 
it exists only on the current screen.
Evidence the team supplies
The team checks recovery, exact references, units, revisions, failed operations, and the contents of 
the export. It checks that the task does not expose unrelated or private material under the actual 
workspace and account arrangement.
If the task changes a scientific calculation, it needs an appropriate reference check. If the calculation 
is unchanged, identify the existing verification and its limits. This assignment does not establish the 
science anew merely by preserving the calculation's inputs.

What this assignment does not require
It does not require a new database, a universal knowledge graph, every scientific module, team 
collaboration, public release, model training, or operating equipment. It does not require Postdoc to 
independently select a scientifically valid parameter.
It also does not require a new ethanol kinetic model, BioSTEAM integration, a batch scheduler, a 
pretreatment comparison, plant-wide economics, or the construction of a complete ethanol process. 
Upstream reference adoption and reproduction receive their own bounded assignment after the 
baseline. Existing calculations should supply this assignment's demonstrable result.
The estimate in this first assignment can be entered by the user. Align checks on the paths actually 
changed, without disguising an estimate as a measurement. Model-generated estimates and their 
wider Postdoc policy change belong in the following bounded assignment within Milestone 1. This 
keeps the first assignment small while preserving the first release's intended behavior.
An export here is a user-controlled copy, not automatic publication. The first example should use 
permitted data, with illustrative or historical material labeled accurately.
What needs to be settled before implementation
The team should recommend the supported calculation, the smallest coherent record change, and the 
recovery and export approach after the baseline check. You confirm the usefulness of the example 
and the behavior described above. You need not choose storage products or programming 
frameworks.
If satisfying this assignment would require a much larger prerequisite than expected, the team should 
explain the practical reason and propose a smaller demonstrable step. It should not quietly turn the 
assignment into an architectural rewrite.
7 Your repeating workflow
Work in understandable rounds
1. Review the next useful outcome. Read its purpose, what you will be able to do, and what counts as 
completion.
2. Clarify the behavior if needed. Describe the difference you want without prescribing how to code it.
3. Authorize the bounded assignment or a coherent group of small assignments. Let the team make 
routine implementation decisions and repair relevant failures within that scope.
4. Try the demonstration. Compare what happens with the stated outcome, including relevant errors 
and recovery.
5. Review the evidence and limits. Get independent technical or domain review where the claim 
warrants it.
6. Record the result, retain a recoverable version, and select the next assignment using what was 
learned.

The unit of review is a useful outcome. You should not be asked to approve every file edit, test run, or 
routine repair. Equally, a large change in purpose, visibility, public rights, or ongoing cost is not a

Questions you can ask without reading code
 What can I do now that I could not do before?
 Where did this value or conclusion come from?
 What survives if I close and reopen the work?
 What happens when an input is missing, a tool fails, or the budget is reached?
 What exactly does this demonstration prove, and what does it leave untested?
 Could someone else understand and repeat the supported work from the records?
A useful report from you is: the estimate is still there, but I cannot find its basis. That identifies a real 
failure in the intended behavior. You do not need to name the faulty function.
Keep a small set of living records
Maintain one home for the vision and requirements, one current-state account, one roadmap, 
important decisions, and the active assignment. They can start as sections of this plan and later move 
into suitable project documents. Avoid maintaining several conflicting copies.
For each assignment, record its outcome, status, evidence, remaining limits, and next step. 
Distinguish planned, in progress, demonstrated as software, and supported by physical evidence

When a new idea appears, decide whether it clarifies the active assignment, fixes a defect, changes

Start with one supported investigation
Default Choose one existing balance, conversion, or recovery calculation for a documented corn-
stover scenario and a narrow useful question. Use permitted example data first. Conversion is batch; 
state recovery and utility modes separately. Switchgrass follows only if suitable evidence and software 
support it. Preserve the larger production and manufacturing ambition in the coverage map.
Who decides The team recommends a technically suitable example. You judge its relevance. A new 
physical procedure requires the people responsible for that work.
Preserve useful implementation
Default Extend existing records and tools where they can support the outcome. A general Study 
concept describes a connected investigation; it does not predetermine a new database, service, or set 
of screens.
When to reconsider The baseline identifies a concrete reliability, recovery, concurrency, or usability 
limit that cannot reasonably be addressed within the existing approach. The team explains the user 
effect and migration implications.

Make estimates useful and honest
Default Allow clearly identified estimates with a stated basis, conditions, and limitations. Preserve

When to reconsider A specific task needs a more formal decision rule or uncertainty method. It

Begin routing with a few meaningful choices
Default Use ordinary software for suitable defined operations and evaluate a small number of useful 
model routes. Record the complete cost of checking and retries as well as the initial call. Retain a 
dependable comparison route. A fallback must respect the same permitted providers, data handling, 
and spending limits; it cannot silently expand them.
When to reconsider A new model, task, or privacy requirement needs evidence of a better route. 
Fine tuning and large agent teams require demonstrated benefit, not a preference for a more 
elaborate architecture.
Let the simple system compete
Default Test the same underlying model on the same bounded engineering questions with 
comparable evidence, installed scientific libraries, permissions and aggregate spending limits. The 
general agent must be competent and allowed to use scientific software. Count every specialist call, 
retry, check and simulation. Begin with a small comparison between real existing paths, using 
separate development and reserved examples.
What we learn Adding checked packaged tools tests their value. Comparing minimal Postdoc with 
that same path plus a specialist tests the specialist. If two proposed conditions are actually identical, 
merge them. Do not build four elaborate systems just to populate a table. Evaluate different model-
routing policies separately so stronger models do not masquerade as an architectural gain.
When to expand A pilot identifies a worthwhile decision, observable variability and an affordable 
comparison. Choose case counts, repetitions and improvement targets from that evidence. No fixed 
percentage saving or quality improvement is promised. An efficient simple path is a valid result. [8]

authority, evidence changes and spending must be explicit. This does not authorize every agent or 
simulator to browse or install software.

Require an understandable completion record
For each completed assignment, the team should state the intended outcome, what changed, what 
was actually checked, how you can try it, remaining limitations, and the next step. Claims that could 
not be verified remain marked as such.
Do not count a feature complete because a screen exists or code builds. Do not count an experiment 
complete because a file contains plausible numbers. Do not erase a failure by changing the expected 
answer without justification.
A mismatch may reveal an implementation defect, a bad test expectation, an unclear requirement, or 
a wrong scientific assumption. Diagnose which one it is and preserve the reason for the correction.
State what a comparison really shows
An independently checkable reference and hard feasibility requirements come before prose quality or 
a low modeled price. Apply a common process and economic boundary. A scenario may be correct 
under its assumptions without demonstrating physical performance. Hypothesis usefulness receives 
its own assessment; it cannot cancel a failed balance or fabricate missing costs.

select an answer. Use reserved cases and repeated trials as resources permit; record sampling and 
stopping rules before inspecting the result. Small pilots can guide development but do not establish 
universal superiority. Compare more than one meaningful allowance when affordable, because a 
baseline may improve with more work. [8, 9]

The first useful software release should demonstrate Milestone 1 on its supported example. It should

10 What we prepare later
The next technical planning stage will turn the first agreed assignment into a concrete implementation 
brief. It will choose the affected parts of the repository, data changes if needed, compatibility 
approach, appropriate checks, and a way to recover from a failed change.
Only then should detailed Codex execution prompts be written. They should refer to the current 
requirements, decisions, assignment, and actual implementation. They should not copy the entire 
history into every prompt or freeze hundreds of future tasks before their dependencies are 
understood.
Postdoc's own research instructions are a separate product responsibility. Changes to them should be 
versioned and evaluated alongside the tools and permissions they depend on. Writing the 
development prompt does not implement those capabilities.
For now, the reviewable result is the plan: one starting investigation, explicit requirements, an order of 
proof, recommended defaults, and a first assignment you can judge. The runtime baseline remains 
the first practical step before implementation.
The revised white paper's flagship and comparison sections provide the scientific and evaluation 
direction. They do not expand the first assignment into a complete plant, a research publication, or a 
large benchmark. The later team handoff should include repeatable reference cases, raw results or 
readable traces, known confounds and unresolved scientific questions as well as working software.
